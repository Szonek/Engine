# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A hobby C++20 game engine ("Engine") plus the ARPG prototype built on it ("Project C"). OpenGL renderer, SDL3 windowing/input, EnTT ECS, Bullet physics, ozz-animation skeletal animation, RmlUi game UI, ImGui/ImGuizmo editor, Tracy profiling.

## Build, run, test

Windows + MSVC and Linux + GCC/Clang are the maintained desktop configurations. FreeType is linked from prebuilt `.lib` files in `thirdparty/freetype` on Windows and from the system (`find_package(Freetype)`) elsewhere; the Linux packages to install are listed in the README and in the Linux CI job. Dependencies are git submodules: `git submodule update --init --recursive`. Only their libraries are built: every dependency's samples, examples, tests and tools are turned off in `thirdparty/CMakeLists.txt`.

The local build tree is `build/` (Visual Studio 17 2022, x64, multi-config). CI and the README use `buildtree/` (CI with Ninja on both platforms). Both are gitignored.

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64          # configure
cmake --build build --config Debug --target project_c_game     # build the game (+ engine, toolkit)
cmake --build build --config Debug                             # build everything: the game and the tests
build\bin\Debug\project_c_game.exe                             # run

cmake --build build --config Debug --target engine_logic_tests scenario_tests
ctest --test-dir build -C Debug                                # all tests
ctest --test-dir build -C Debug -L ci                          # only the tests CI runs
ctest --test-dir build -C Debug -L gpu --output-on-failure     # scenario tests (real game code, needs a GL 4.5 context)
build\bin\Debug\engine_logic_tests.exe --gtest_filter=Suite.Name   # single test

cmake --build build --config Release --target big_scene_benchmark
build\bin\Release\big_scene_benchmark.exe --out results.md     # frame times of big scenes (GPU, visible window; not a test)
```

Benchmarks live in `src/tests/benchmarks` (see its README for options and the baseline numbers); rerun the big scene benchmark after changes to rendering, physics, transforms or scripts and compare with the baseline.

Binaries land in `build/bin/<Config>/`, libraries in `build/lib/<Config>/`.

On Linux (single-config, e.g. Ninja; binaries in `build/bin/`):

```bash
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug
cmake --build build
ctest --test-dir build -L ci
LIBGL_ALWAYS_SOFTWARE=1 xvfb-run -a ctest --test-dir build -L gpu --output-on-failure   # scenario tests without a GPU: Mesa's software GL on a virtual X server
```

Things that will trip you up:

- **Sources are listed explicitly** in each `CMakeLists.txt` (no globbing). A new `.cpp`/`.h` must be added to the list by hand.
- **The asset path is baked in at configure time**: `PROJECT_C_ASSETS_DIR` (set in `src/games/project_c/CMakeLists.txt`) points at the `assets/` folder of the source tree the game was built from, so a worktree build uses its own shaders. Shaders, models, fonts and UI documents are loaded from there at runtime, so asset edits need no rebuild.
- **With the editor enabled** (`enable_editor = true` in `app.cpp`) the game starts in Play mode; the Pause button stops it. Scripts only tick while the editor is in Play mode — see `IScene::update`.
- `engine_logic_tests` (in `src/tests/unit_tests`) compiles the engine sources under test (render graph, shadow maths, the header-only resource atlas and ID registry, skins and the animation controller, the nav mesh build and queries, the type registry and scene files, with a stub logger that records what was logged, `test_logger.h`; Tracy/RmlUi only as headers, so the profiling macros are empty) directly and needs neither GL nor the engine DLL. **Add new GL-free tests to it** instead of creating another executable; tests that need a GL context belong in `scenario_tests`.
- **Scenario tests** (`src/tests/scenario_tests`) run real gameplay code: the game is built as the static library `project_c_lib` (everything but `main.cpp`), which the test links. One `AppProjectC` is created for the whole run (`AppConfig` in `app.h`: hidden window, editor off so gameplay is never paused; no level is registered). A test derives from `scenario::ScenarioTest`, loads its own `IScene` with `load_scene<T>()` and advances it with `step(frames)`: every frame simulates exactly `FIXED_DT_MS` (1/60 s) whatever the real frame time, so runs are deterministic. Input: gameplay scripts read `project_c::PlayerInput` (`player_input.h`: move directions, attack, dodge, interact, drop weapon, cursor) from `AppProjectC::player_input()`, never the keyboard/mouse directly; `read_player_input_from_devices` is the only place that reads them. Whoever drives the frames sets it: the game's main loop fills it from the devices each frame (the key bindings live in `read_player_input_from_devices`), scenario tests set it with `set_input(...)`, which holds until changed. Delta times are in **milliseconds** throughout the engine and scripts; `engineFrameBegin` caps the frame time at the app's `max_delta_time` (1/3 s by default, like Unity's Maximum Allowed Timestep), so the long first frame after loading doesn't throw the game forward. Frames still render (in a 320x180 window) but are never presented, so a frame costs well under 1 ms; most of the suite's time in Debug is loading the prefabs once (~7 s). Gameplay scenarios use `scenario::SandboxScene` (`sandbox_scene.h`: camera, light, `Encounter`, no HUD) and place only what they need with `scene->build()` (the game's `LevelBuilder`); `GameplayTest::step_aiming` points the cursor at a world position. **Tests of the engine itself (prefabs, asset IDs, animation controllers) never use the game's models**, which will be replaced: they load the generated glTF models in `assets/models/test_fixtures` (`test_models.h`: `TestModel` loads one as a prefab and releases it with the test, `ModelTest` is the fixture with an empty scene). Add a model to `generate_test_models.py` (standard library only, deterministic output) and regenerate instead of editing the files; its docstring lists them. Tests of game scripts (`character_asset_tests.cpp`, gameplay, level) use the game's prefabs and should assert outcomes, not model details.
- There is no linter or formatter config. `-Werror` is only applied to the engine on non-MSVC compilers (GCC on Linux CI, Clang locally), so code MSVC accepts can still fail there: include what you use (MSVC pulls in `<cstdint>`/`<cstring>` transitively), no MSVC-only extensions (e.g. `__m128::m128_f32`), and a `.cpp` must be valid UTF-8 for Clang. Third-party headers are included as SYSTEM so their warnings don't count.
- CI (`.github/workflows/cmake-single-platform.yml`) has two jobs. Windows builds Release and runs the tests labelled `ci` (`set_tests_properties(... LABELS ci)`); the runner has no GPU, so GL-dependent tests must not get that label. Release compiles out `assert`, so tests must check return values or state, not rely on an assert firing. Linux builds Debug with GCC and runs the `ci` tests and the `gpu` scenario tests on Mesa's software renderer under Xvfb (GL 4.5 core, so a scenario run takes ~2 min there; the test's timeout is a hang guard). Both jobs pin CMake 4.4.4 and build with Ninja and a compiler cache (sccache on Windows, ccache on Linux), so an unchanged file is not compiled again.

## Architecture

Three layers, each depending only on the one below:

```
src/games/project_c        executable  - gameplay: scenes, scripts, prefabs
src/engine_app_toolkit     shared lib  - C++ convenience layer: IApplication / IScene / IScript
src/engine                 shared lib  - the engine, exposed through a C API only
```

### Engine (`src/engine`)

- `include/` is the **entire public surface**: a C API in `engine.h` plus plain C structs for components in `include/components/`. Nothing in `impl/` is visible to the game or toolkit.
- `impl/engine.cpp` is the C API boundary. Opaque handles are converted to internal C++ types with the `api_cast` overloads at the top of the file; `engine_game_object_t` is an `entt::entity`.
- `engine_game_object_t` changes between runs; **files reference game objects by their persistent ID**, which is engine-internal (`Scene::get_persistent_id`; the engine's serializer translates references, so there is no public API for it). `Scene::create_new_entity` gives every entity one from a per-scene counter (`impl/entity_id_registry.h`, never reused), so building a scene in the same order gives the same IDs. The game objects inside a persistent prefab instance (all but its root) get **hashed IDs** instead: `EntityIdRegistry::hashed_id(root ID, node path)` with the top bit set (counter IDs stay below 2^63 and hashed ones never move the counter), like Unity's file IDs of the objects in a prefab instance, so a reference into an instance survives a reload however many game objects were created before it (`Scene::create_prefab_node_entity`; a hashed ID in use already is logged and replaced by a counter ID). Objects which aren't scene content are **transient**: no persistent ID, so they don't shift the IDs of the others, and never saved. Editor-only objects use `Scene::create_transient_entity`; games use `engineGameObjectCreateTransient` / `enginePrefabInstantiateTransient` for objects spawned at runtime (`engineGameObjectIsTransient`).
- The API is **context based**: `engineApplicationSetActive` / `engineSceneSetActive` store globals (`G_ACTIVE_APP`, `G_ACTIVE_SCENE`) and nearly every other call (`engineGameObject*`, `engineFrame*`, `enginePhysics*`, input) acts on the active app/scene without taking a handle. The API example in `README.md` predates this and is out of date — trust `engine.h`.
- Components are value types across the boundary: `engineGameObjectGet*Component` returns a copy and changes only take effect after `engineGameObjectUpdate*Component`. Internally that is an EnTT `replace`, and `Scene` / `PhysicsSystem` rely on the registry's update signals (`on_update` listeners, and a reactive storage of moved transforms) to rebuild/sync Bullet bodies.
- **Derived data never lives in authored (public) components**: it goes into engine-internal components that the scene computes and that are never saved (world matrix, skin pose, animation controller, children list, nav mesh). The transform component is only the authored local TRS, relative to the parent space (the parent's world matrix, times the joint matrix when the game object has a joint attachment; the world when it has neither). The world matrix is `world_transform_internal_component_t` (`impl/world_transform.h`, GL-free and unit tested), added and removed with the transform component; the game reads it with `engineGameObjectGetWorldTransform`, valid after the last scene update. To write a world matrix back (editor gizmo, physics), convert it with `local_transform_from_world` against `Scene::get_parent_space_matrix`.
- Hierarchy: the parent component is the only thing to set. A game object's children are derived from the parent components of the others (`children_internal_component_t`, kept by `Scene`'s listeners, in the order they were parented, no size limit) and are queried with `engineGameObjectGetChildrenCount` / `engineGameObjectGetChild`; any hierarchy change invalidates the indices, so copy the children before destroying or reparenting them (`project_c::utils::get_children`). Destroying a game object (`engineGameObjectDestroy`, also when its `IScript` is destroyed) destroys its children with it; remove a child's parent component first to keep it. Organizing the editor's scene hierarchy view is **not** done with parents: the folder component (`engine_folder_component_t`, a `/` separated path such as `environment/walls`) lists a game object that has no parent in a folder, and has no other effect.
- Adding a component type means touching: the C struct in `include/components/`, the Add/Get/Update/Remove/Has functions in `engine.h` + `engine.cpp`, any default-initialisation in `impl/components_utils/components_initializers`, the consuming system in `scene.cpp`, its description in `impl/serialization/builtin_types.cpp` when it holds authored data (so scene files save it; at the place in the load order its listeners need), and (optionally) the properties panel in `application_editor.cpp`.
- `Application` owns the window/GL context, resource atlases (textures, geometries, skins, animation sets, prefabs, shaders — `named_atlas.h`, addressed by handle or name; names must be unique and non-empty, so creation fails otherwise; every asset is **reference counted** (`add_object` gives one reference, `acquire` / `release`, the last release destroys it) and a **handle is slot + generation** (generations start at 1, so no handle is 0: `ENGINE_INVALID_OBJECT_HANDLE` is 0, like `ENGINE_INVALID_GAME_OBJECT_ID`, and a zeroed struct references no asset; the other ids of the API, component types and animation events, never are 0 either), so a handle to a released asset never finds anything again, not even an asset created later in its slot (lookups return `nullptr` / `ENGINE_INVALID_OBJECT_HANDLE`; the renderer skips and logs such draws). Components store handles **without** holding references (they are values copied across the C API): whoever loads an asset holds it, and the names are the asset IDs scene files will use: a model file is named by its path relative to `assets/models` (`/` separators, e.g. `KayKit_Adventurers_1.0_FREE/Characters/gltf/Rogue.glb`), so an ID alone is enough to load it; glTF meshes, embedded images and skins are `<model path>#<name>` (`#mesh_<i>` etc. when unnamed, see `impl/asset_id.h`), e.g. `<…>/Rogue.glb#Cylinder.008` (the game builds them with `AppProjectC::model_asset_id`); an image in its own file is named by its path relative to `assets/models` too, so models referencing it share one texture), the `UiManager` and the `Renderer`. `ApplicationEditor` derives from it and is instantiated instead when `enable_editor` is set; it hooks the `on_*` virtuals to add the ImGui dockspace (the scene is rendered into a texture at the size of its scene panel and shown there, see `get_scene_viewport`), editor camera, gizmos, entity picking, undo (`editor_commands`) and the Play/pause + game/editor view state that `engineEditorIsPlaying` / `engineEditorIsGameView` report.
- `Scene` owns the EnTT registry and a `PhysicsSystem` (`impl/physics_system.h`, reached with `Scene::physics()`): the ECS side of physics (body types, creating bodies from their components, syncing them to transforms, forces, writing dynamic bodies back, character moves, queries) around a `PhysicsWorld`, the Bullet side. Keep physics code there, not in `Scene`. `Scene::update` runs animation controllers → physics (sync bodies to the transforms, step, write dynamic bodies back) → world transforms (`update_world_transforms`: TRS, joint attachments, parent→child; writes only the internal component, so no observers fire) → skins, then gathers a `SceneRenderData` and submits it. It never calls the graphics API. **Physics always sees this frame's state, also during the scripts' update** (like Unity: eager bodies, lazy transform sync): a body is created as soon as its collider / rigid body / character controller is added and again when one changes, at the world matrix computed from the current transforms (`compute_world_matrix`, not the world transform component, which is from the last update); moved transforms are synced to the bodies before the physics step and before every physics query (ray cast, character move) when a transform, parent or joint attachment changed (`PhysicsSystem::sync_bodies_to_transforms`). Bodies of game objects with a parent or joint attachment follow it, the others move when their transform changes. Collider sizes are in their game object's space: the shape is scaled by the world scale, inherited from the parents (a hitbox under a character scaled 0.35 is authored in the character's units). **Body types are explicit** (`engine_rigid_body_type_t`, like Bevy/Jolt/Godot): dynamic (moved by the physics, needs mass), kinematic (moved by its transform; Bullet gives it a velocity, so it pushes dynamic bodies) or static (level geometry). A collider without a rigid body is static, or kinematic when it has a parent or joint attachment (hitboxes); an explicit type wins (e.g. static walls parented to a room). The engine never infers a type from movement: a static collider moved by its transform is teleported, and logged once outside the editor. Kinematic bodies pair with dynamic and kinematic ones but not with statics, so a hitbox detects a character (whose capsule is kinematic); static colliders never detect each other; bodies moved by hand go through `PhysicsWorld::set_world_transform`, which also updates their broadphase bounds so ray casts see them immediately (Bullet steps at a fixed 1/60 s, so a frame can have no substep). Ray casts (`enginePhysicsRayCast`: origin, direction, max distance, like Unity's `Physics.Raycast`) skip triggers unless their filter asks for them. A collider with `disable` set (like Unity's `Collider.enabled`) keeps its shape but has no body: nothing collides with it, no ray cast hits it and nav mesh builds leave it out.
- Rendering is a render graph; **read `src/engine/impl/render/README.md` before changing anything under `render/`**. It covers the pass list, how to write a pass, and the `RenderFeature` extension point (post-process and overlay stages). `render_graph.h/.cpp` must stay free of GL so it remains unit-testable.
- Animation: `Skin` + `AnimationController` wrap ozz. A `Skin` is a shared, immutable **asset** in the skins atlas (skeleton + binding to the mesh; the model's prefab creates one per model, not per instance). Each instance's pose (`SkinPose`) lives in an internal component (`skin_pose_internal_component_t`) on the game object with the skin component, created in the rest pose when that component gets its skin; the animation controller on the same game object writes it. Skinned meshes and joint attachments reference that **game object** (`.skin` is an `engine_game_object_t`), not the asset, because the asset alone can't say whose pose to read. A model's clips compiled for its skin are an **animation set** asset (`AnimationLibrary`, atlas name `<model path>#animations`, one per model, created by the prefab). **Controllers are owned by the engine**: the animation controller component holds the animation set handle and the **layer setup as data** (per layer: an optional descriptive name, mode, starting weight, starting looping, joint weights as a mask; layer id = index, scripts address layers by id; a new component has one override layer). When it gets a set (and the game object has a skin), `Scene` creates the controller in an internal component (`animation_controller_internal_component_t`) and it is destroyed with the component, the skin component or the game object; an update with the same set and skin only reconfigures the layers (the controller and its animation events stay). No controller pointer leaves the engine: the `engineAnimationController*` functions take the **game object** and act on its controller. They are runtime commands and queries only (play, cross-fade, is playing, events, and changing a layer's weight / looping / playback rate while playing); the layer setup is never done through calls (like `enginePhysicsAddForce(go, …)` on its body), returning false / an error code when it has none. The editor's stats show the number of live controllers (`AnimationController::get_live_count`).
- **Characters are moved by the engine's kinematic character controller** (`engine_character_controller_component_t`, like Unity's `CharacterController` / Godot's `move_and_slide`, not by physics forces): a capsule standing on the game object's origin (sizes in its scaled space, like colliders). Scripts call `engineCharacterControllerMove(go, velocity, dt, &result)` once per frame with the horizontal velocity they want; the engine adds gravity (keeping the fall speed between moves, in `character_controller_internal_component_t`) and sweeps the capsule (`PhysicsWorld::move_character`): step up, collide and slide horizontally (everything is slid along, never climbed), step down and snap to walkable ground (ledge detection: the edge of walkable ground counts; a step is only taken when it ends on walkable ground). Static and kinematic bodies block it (including other characters), triggers and dynamic bodies don't (its kinematic capsule pushes those). The transform is written right away; while a script doesn't call it (the player's scripted traversal), setting the transform moves the character. Don't combine it with a collider or rigid body; the game object must have no parent.
- **Navigation is engine-owned** (Recast/Detour, `impl/nav_mesh.h`). Authored: one **nav surface** component per scene (agent radius/height/max slope/max climb, cell size/height) and optional **nav modifier** components (like Unity's `NavMeshModifier`: walkable = included by the normal rules, the default; not walkable = obstacle; ignore = left out; children inherit their closest ancestor's). `engineNavMeshBuild()` rasterizes the scene's **static colliders** at their world transforms (colliders of kinematic rigid bodies, dynamic ones with mass and triggers are skipped; without a modifier the slope decides what is walkable) into one single-tile nav mesh, logs its triangle count and build time, and keeps it in an internal component on the nav surface's game object (`nav_mesh_internal_component_t`: derived data, never saved, destroyed with the surface). Nothing rebuilds it automatically: build it after placing or loading the level and again after static colliders changed. Floors made of many tiles need no merging, Recast voxelizes all input into one heightfield. Queries take the caller's search extents for snapping points onto the nav mesh: `engineNavFindPath` (string-pulled corners, start first, with a complete/partial status; partial when the end is unreachable, e.g. on a disconnected island, then it ends at the closest reachable point) and `engineNavFindNearestPoint`. The editor has a nav mesh debug-draw toggle (scene options) and a "Build nav mesh" button under the Nav Surface component (the bake: after editing the surface, modifiers or static colliders).
- **Prefabs are engine assets** (`impl/prefab.h`, `prefabs` atlas, named by the model's path, e.g. `KayKit_Adventurers_1.0_FREE/Characters/gltf/Rogue.glb`): `enginePrefabLoad` parses a glTF file and creates its geometries, textures, skin and animation set as assets (the `<model path>#<name>` IDs above) which live as long as the prefab; loading a file which is loaded already returns the same prefab with one more reference. An image in its own file is a dependency, not a sub-asset: each prefab using it (and the game, if it created it with `engineTexture2DCreateFromFile`) holds a reference, so it lives as long as the last of them. `enginePrefabRelease` drops the caller's reference; every instance holds one too, so a prefab is destroyed (with its assets) when the game has released it and its last instance is destroyed, at the latest with its scene. Release prefabs before their application is destroyed, and keep a prefab loaded while game objects which aren't its instances use its assets (e.g. the player's weapon uses `<…>/Rogue.glb#Cylinder.008`; the game holds its prefabs for its whole run). `enginePrefabInstantiate` stamps the model's node hierarchy into the active scene (joints of the skin become no game objects, the root parents everything) and marks the root with an internal `prefab_instance_internal_component_t` (`enginePrefabInstanceGetPrefab`; it holds the instance's reference to the prefab and a `PrefabInstanceInfo`: the instance's game objects by node path and the registered components the prefab gave each of them, captured right after instantiation, which scene files use). Both go through `PrefabSystem::instantiate_prefab` (`impl/prefab_system.h`, the scene's prefab instances, reached with `Scene::prefabs()`, like `PhysicsSystem`). A node's path is the node names from the root down, joined by `/` ("" for the root; a name which is empty or used by an earlier sibling gets its position: `Arm#1`). The glTF parser's model description (`ModelDesc`) is internal: the C API has no model/mesh/skin desc types.
- **Scene files** (`impl/serialization/`, JSON via rapidjson): `engineSceneSave` / `engineSceneLoad` (paths relative to `assets/scenes`, or absolute) save the active scene's authored data and add a file's game objects to it (`Scene::save` / `Scene::load` do it in memory, for the engine itself: the editor's undo of a delete saves the game object and what is parented under it (`save_game_objects`) and loads it back with the same handles and references to the rest of the scene (`SceneLoadOptions`), and the future Play/Stop restore). The engine owns reflection (Flecs-style): `TypeRegistry` (`type_registry.h`, GL-free) describes C structs field by field (`TypeBuilder` with member pointers: plain fields, enums by name, nested structs, tagged unions, asset and game object references) and gives components type-erased storage that works like the C API (add with defaults, get, update). `builtin_types.cpp` registers the engine's components with authored data, **in load order** (transform and parent before what reads world matrices, rigid body before collider); skins, animation controllers and joint attachments aren't described yet (they come with prefab instances). `scene_serializer` (GL-free, unit tested) writes every game object with a persistent ID, sorted by ID, every field (defaults too), enums by name, assets by asset ID, references by persistent ID, a union's active case only, so the same scene gives the same bytes; a **prefab instance** is saved as its root with `"prefab"` (the prefab's asset ID), the root's name and transform (always saved, like Unity's instance root overrides) and the components added to the instance after it was created, on the root or under `"nodes"` by node path; the rest of what the prefab created is not written, and changes to it can't be saved yet (overrides are phase 3): saving logs them once per instance. The serializer reaches instances through `IPrefabInstances` (`serialization/prefab_instances.h`, implemented by `PrefabSystem`, faked in the unit tests). Loading checks the whole file before changing anything, then creates every game object (keeping the file's IDs; a used one gets a new ID and the file's references follow it), instantiates the prefab instances into their roots (the file's references to their game objects use the hashed IDs of the file's root ID; a prefab which can't be found leaves the root alone, a node the model doesn't have is logged and references to it are none) and adds the components type by type the C API way, so the scene's listeners run; problems inside a usable file are logged and skipped. The scene's `SceneAssets` resolves asset IDs, loading the model (`<model path>#<name>`) or image file on demand, and holds one reference per file until the scene is destroyed. **Game-defined components** (`serialization/game_types.h`): the game describes its own plain C structs field by field through the C API (`engineComponentTypeRegister`, `engineStructTypeRegister` for structs inside them; a field desc per member with `offsetof`, kinds as in the registry but **no unions** (only the engine's components use them; a game describes each case as its own field or component), structs of the game's own struct types, game object / geometry / texture handles as their own kinds) and uses them with `engineGameObject{Add,Get,Update,Remove,Has}DataComponent(go, type, ...)` (whole-struct copies, like the engine's components; only for game-defined types, the engine's have their own functions); `engineComponentViewAttachDataComponent` iterates the game objects with one and `engineDataComponentGetChangeCount` counts its adds, updates and removes in the active scene (kept in the registry's context), so a caller sees a change without iterating every frame. A field desc may carry **editor hints** (`flags`: read-only, hidden, range with `range_min`/`range_max`; a `tooltip`) and `ENGINE_FIELD_KIND_COLOR` is a float[3]/[4] colour saved as its floats (`FieldInfo::hints`, drawn by the inspector: colour picker, clamped drags); hints never change what is saved. A type without a default value starts zeroed, which references nothing (see the handles above). Descriptions are checked: fields within the struct, hints that fit their field (a range on a number, within its type), aligned (not more than the struct) and not overlapping, unique names, known struct types, enums with unique named values, storage ids that don't collide. (For the engine's types with unions, `TypeBuilder` also checks that no union case is written under another field's key, `type_builder_detail::find_duplicate_key`, and the loader starts a case whose tag changed zeroed, `clear_union`.) They go into the same `TypeRegistry` (`TypeInfo::game_defined`), after the engine's types, so they are saved and loaded after the engine's components; each type has its own EnTT storage under a runtime id (`registry.storage<DataBlob<N>>(hash(name))`: a packed array like the engine's components, in slots of the type's size rounded up to 16 bytes, `data_slot_size`; at most `ENGINE_COMPONENT_TYPE_MAX_SIZE`), destroyed with its game object; nothing in the engine listens to them (the only listener connected to these storages' signals is the change count's, on their destroy signal, so a component destroyed with its game object counts as removed). Register types once after the application is created, before loading a file holding them; they can't be unregistered. The editor's properties panel draws them from their descriptions (`TypeInspector` / `display_typed_component` in `application_editor.cpp`: a widget per field kind, asset combos, game objects picked by name and persistent ID; edits, Add and Remove go through `CommandUpdateTypedComponent` / `CommandAddTypedComponent` / `CommandRemoveTypedComponent`, so they undo); engine components keep their hand-written panels.
- `impl/imgui` and `impl/imguizmo` are vendored copies compiled into the engine, not the submodules of the same name.
- Shaders live in `assets/shaders`; the `#version` line is added implicitly by the engine, so shader files must not declare it. `*.h` files there are shared GLSL includes.

### Toolkit (`src/engine_app_toolkit`)

Thin C++ wrappers over the C API that define the game-side object model:

- `IApplication` creates the engine application and owns a `SceneManager` (scenes are registered by type and looked up by their static `get_name()`).
- `IScene` owns one engine scene and a map of `engine_game_object_t → IScript`. One script owns one game object.
- **Scripts are data** (`script_registry.h`, like Unity's MonoBehaviour reference or Godot's script property, but the engine never knows scripts): a game object's script is its `script` component, a game-defined component the toolkit registers whose field is an enum of the script type names (`ScriptRegistry`, `IApplication::scripts()`; the game registers every script type at startup with `add<T>(name, required components)`, then `register_component()`). Scene files save it and the editor edits it (a dropdown). At the start of `IScene::update` the scene creates the script a script component names, replaces it when the component changes and removes it when the component goes (keeping the game object), looking at the components only when `engineDataComponentGetChangeCount` moved, never every frame. `IScene::attach_script<T>(go)` sets the component and creates the script at once (level code that needs the pointer); the components a script type requires are added with their defaults when missing (like Unity's `RequireComponent`). A script created from data takes only `(IScene*, engine_game_object_t)`. Runtime scripts with other arguments (a weapon's hitbox knowing its enemy) are registered by code (`register_script<T>(args...)`) and have no script component.
- **Script lifecycle** (`iscene.h`, like Unity `Awake`/`Start`, Godot `_ready`, Unreal `BeginPlay`): a script's **constructor adds nothing that is saved**: what its game object is made of (name, transform, colliders, its config component) is level content, placed by `LevelBuilder` or loaded from a scene file; the constructor may only do runtime setup of its own game object (its animation layers, removing model parts it doesn't use) and never creates other game objects or looks up other scripts. Everything involving other objects goes into `on_start()`: called once, before the first `update`, after every script registered in the same frame is in the map (so they can find each other), in registration order; scripts registered in `on_start` start in the same frame. While the editor is paused, scripts wait for Play to start. **Objects a script spawns are runtime objects: transient**, never saved (`AppProjectC::spawn_prefab`, `engineGameObjectCreateTransient`); level content is placed by the level (`LevelBuilder`) and found by scripts in `on_start`.
- `IScene::update` defines the frame order: sync the scripts with the script components → flush newly registered scripts and `on_start` them → (if playing) `update_hook_begin`, dispatch physics collisions to `on_collision`, `update`, `late_update` → `engineFrameSceneUpdate` → drop scripts whose game object was destroyed → `update_hook_end` → flush unregistrations. Script registration and unregistration are **deferred through queues**, so a script registered this frame is not in the map until the next `update`.
- `utils.h` has the `set_c_array` / `to_array` helpers for the C-array fields in component structs, and `log()`.

### Project C (`src/games/project_c`)

- `default_prefabs_data()` (`app.cpp`) maps `PrefabType` → glTF file; `AppProjectC` loads each as an engine prefab once at startup (and releases them in its destructor); `instantiate_prefab()` instantiates one into the active scene (level content) and returns its root as a `PrefabResult`; `spawn_prefab()` instantiates a transient one (runtime objects spawned by scripts: the player's weapon and attack trigger, enemy blades, coins).
- `main.cpp` registers the level scene and owns the main loop, which holds only platform concerns: `engineFrameBegin` → read the devices into `PlayerInput` → quit (window closed or the `quit` action) → `AppProjectC::update(dt)` → `engineFrameEnd`. `AppProjectC::update` is one game frame: update the scenes, then apply scene changes they requested (`request_scene_reload<T>()`, deferred because a scene can't replace itself mid-update). Scenario tests call the same function. **Level rules live in the scene** (`TestScene::update` override: gameplay UI visibility, restart once the encounter is over), never in the loop and not in `AppProjectC`, which stays level-agnostic. There is a single level, `scenes/scene_test.cpp`: it builds the ASCII map with `LevelBuilder`, builds the nav mesh (`engineNavMeshBuild`) once the map is placed, and adds the camera, light, `Encounter` and `GameplayHud` scripts.
- **Gameplay scripts never depend on the scene class.** Win/lose rules are the `Encounter` script (`scripts/encounter_script.h`: cleared when every enemy is dead, defeated when the player is), and the HUD is the `GameplayHud` script (owns the RmlUi document `assets/ui_docs/project_c_gameplay_ui.rml` and its data bindings). Both *read* the Player/Enemy/Weapon scripts every frame; nothing reports to them. Scripts that need them use `my_scene_->find_script<Encounter>()` and must handle `nullptr`: a scene without an encounter or HUD (e.g. a scenario test scene) still plays.
- `scenes/level_builder.h` places the camera, the main light, the `Encounter` and `GameplayHud`, the nav surface, floor tiles (`floor_not_walkable` adds a not-walkable nav modifier), walls, static obstacles, the player (which spawns and equips its starting weapon when it starts), enemies, chests, weapons and the house (its walls, window and roof are `BuildingPart` children of the `House`, which stands at the center of its floor). Each object gets its components and, when it has behaviour, its script as data (`attach_script`), so a built scene is what its scene file would load. The level and the scenario tests both build with it. Floors, walls and the light have no behaviour, so no script (`Floor` is kept as a marker: a dropped weapon lands on it).
- **Designer-set values are game components** (`scripts/game_components.h`, registered by `AppProjectC::register_script_types` before the scripts): `EnemyConfig`, `PlayerConfig`, `BuildingPartConfig`, `HouseConfig` (roof props as game object references), with editor hints (ranges, tooltips, a colour). Scripts read them **on every use** (`Enemy::config()`, `get_game_component`), so an edit in the editor while playing takes effect at once; runtime state (hp, cooldowns) stays in the scripts' members and is never saved. The scripts which need one declare it as required.
- Gameplay objects are scripts deriving from `BaseNode` (`scripts/base_script.h`), which is `IScript` plus a constructor naming runtime (transient) objects. Player and enemy logic are hand-written state machines driving animation-controller layers and animation events; scripts find each other through `my_scene_->get_script<T>(go)` (returns `nullptr` when the game object has no script of that type), or `find_script<T>()` / `get_scripts<T>()` for scripts that aren't tied to a known game object.
- `CameraScript` follows the player with a spring and shifts toward the mouse cursor (look-ahead). Occlusion is handled only by the house itself: while the player is inside, `House` hides the roof (and the props on it) and the camera facing wall.
- Player traversal and camera occlusion are documented in `src/games/project_c/CLIMBING_AND_OCCLUSION.md`. Player traversal (climb a wall, vault through a window, climb down a roof edge, mantle onto the roof at the top of a climb) starts automatically when the player walks into the obstacle; a pulsing marker shows the nearest available action whenever the player is close to a wall, window or roof edge. On the wall, WASD keeps its ground meaning: toward the wall climbs up, away climbs down. It is raycast-driven and only reacts to colliders owned by `BuildingPart` scripts (`scripts/building_script.h`). While traversing, the traversal code sets the player's transform and its character controller isn't moved; walking (and falling) resumes when traversal ends. The `House` is built over the `h` cells of the ASCII map in `scene_test.cpp`; those cells get floor tiles with a not-walkable nav modifier, so enemies don't path into the house. Enemies query paths with `engineNavFindPath`; the scenario `SandboxScene` builds its nav mesh before its first step.
