# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A hobby C++20 game engine ("Engine") plus the ARPG prototype built on it ("Project C"). OpenGL renderer, SDL3 windowing/input, EnTT ECS, Bullet physics, ozz-animation skeletal animation, RmlUi game UI, ImGui/ImGuizmo editor, Tracy profiling.

## Build, run, test

Windows + MSVC is the only maintained desktop configuration (FreeType is linked from prebuilt `.lib` files in `thirdparty/freetype`). Dependencies are git submodules: `git submodule update --init --recursive`.

The local build tree is `build/` (Visual Studio 17 2022, x64, multi-config). CI and the README use `buildtree/` with NMake. Both are gitignored.

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64          # configure
cmake --build build --config Debug --target project_c_game     # build the game (+ engine, toolkit)
cmake --build build --config Debug                             # build everything, including all thirdparty samples (slow)
build\bin\Debug\project_c_game.exe                             # run

cmake --build build --config Debug --target engine_logic_tests scenario_tests
ctest --test-dir build -C Debug                                # all tests
ctest --test-dir build -C Debug -L ci                          # only the tests CI runs
ctest --test-dir build -C Debug -L gpu --output-on-failure     # scenario tests (real game code, needs a GPU)
build\bin\Debug\engine_logic_tests.exe --gtest_filter=Suite.Name   # single test
```

Binaries land in `build/bin/<Config>/`, libraries in `build/lib/<Config>/`.

Things that will trip you up:

- **Sources are listed explicitly** in each `CMakeLists.txt` (no globbing). A new `.cpp`/`.h` must be added to the list by hand.
- **The asset path is baked in at configure time**: `PROJECT_C_ASSETS_DIR` (set in `src/games/project_c/CMakeLists.txt`) points at the `assets/` folder of the source tree the game was built from, so a worktree build uses its own shaders. Shaders, models, fonts and UI documents are loaded from there at runtime, so asset edits need no rebuild.
- **With the editor enabled** (`enable_editor = true` in `app.cpp`) the game starts in Play mode; the Pause button stops it. Scripts only tick while the editor is in Play mode — see `IScene::update`.
- `engine_logic_tests` (in `src/tests/unit_tests`) compiles the engine sources under test (render graph, shadow maths, the header-only resource atlas and ID registry, skins and the animation controller, the nav mesh build and queries, with a stub logger; Tracy/RmlUi only as headers, so the profiling macros are empty) directly and needs neither GL nor the engine DLL. **Add new GL-free tests to it** instead of creating another executable; tests that need a GL context belong in `scenario_tests`.
- **Scenario tests** (`src/tests/scenario_tests`) run real gameplay code: the game is built as the static library `project_c_lib` (everything but `main.cpp`), which the test links. One `AppProjectC` is created for the whole run (`AppConfig` in `app.h`: hidden window, editor off so gameplay is never paused; no level is registered). A test derives from `scenario::ScenarioTest`, loads its own `IScene` with `load_scene<T>()` and advances it with `step(frames)`: every frame simulates exactly `FIXED_DT_MS` (1/60 s) whatever the real frame time, so runs are deterministic. Input: gameplay scripts read `project_c::PlayerInput` (`player_input.h`: move directions, attack, dodge, interact, drop weapon, cursor) from `AppProjectC::player_input()`, never the keyboard/mouse directly; `read_player_input_from_devices` is the only place that reads them. Whoever drives the frames sets it: the game's main loop fills it from the devices each frame (the key bindings live in `read_player_input_from_devices`), scenario tests set it with `set_input(...)`, which holds until changed. Delta times are in **milliseconds** throughout the engine and scripts; `engineFrameBegin` caps the frame time at the app's `max_delta_time` (1/3 s by default, like Unity's Maximum Allowed Timestep), so the long first frame after loading doesn't throw the game forward. Frames still render (in a 320x180 window) but are never presented, so a frame costs well under 1 ms; most of the suite's time in Debug is loading the prefabs once (~7 s). Gameplay scenarios use `scenario::SandboxScene` (`sandbox_scene.h`: camera, light, `Encounter`, no HUD) and place only what they need with `scene->build()` (the game's `LevelBuilder`); `GameplayTest::step_aiming` points the cursor at a world position. **Tests of the engine itself (prefabs, asset IDs, animation controllers) never use the game's models**, which will be replaced: they load the generated glTF models in `assets/models/test_fixtures` (`test_models.h`: `TestModel` loads one as a prefab and releases it with the test, `ModelTest` is the fixture with an empty scene). Add a model to `generate_test_models.py` (standard library only, deterministic output) and regenerate instead of editing the files; its docstring lists them. Tests of game scripts (`character_asset_tests.cpp`, gameplay, level) use the game's prefabs and should assert outcomes, not model details.
- There is no linter or formatter config. `-Werror` is only applied to the engine on non-MSVC compilers.
- CI (`.github/workflows/cmake-single-platform.yml`) builds Release on Windows and runs the tests labelled `ci` (`set_tests_properties(... LABELS ci)`). The runner has no GPU, so GL-dependent tests must not get the label. Release compiles out `assert`, so tests must check return values or state, not rely on an assert firing.

Android: `android-project/` is a Gradle wrapper around the root `CMakeLists.txt` (arm64-v8a); the game is built as a shared library there. `K_IS_ANDROID` in the toolkit's `utils.h` gates platform differences.

## Architecture

Three layers, each depending only on the one below:

```
src/games/project_c        executable  - gameplay: scenes, scripts, prefabs
src/engine_app_toolkit     shared lib  - C++ convenience layer: IApplication / IScene / IScript
src/engine                 shared lib  - the engine, exposed through a C API only
```

### Engine (`src/engine`)

- `include/` is the **entire public surface**: a C API in `engine.h` plus plain C structs for components in `include/components/`. Nothing in `impl/` is visible to the game or toolkit.
- `impl/engine.cpp` is the C API boundary. Opaque handles are converted to internal C++ types with the `api_cast` overloads at the top of the file; `engine_game_object_t` is an `entt::entity`.
- `engine_game_object_t` changes between runs; **files reference game objects by their persistent ID**, which is engine-internal (`Scene::get_persistent_id`; the engine's serializer translates references, so there is no public API for it). `Scene::create_new_entity` gives every entity one from a per-scene counter (`impl/entity_id_registry.h`, never reused), so building a scene in the same order gives the same IDs. Editor-only objects use `Scene::create_transient_entity` so they don't shift the IDs of the game's objects.
- The API is **context based**: `engineApplicationSetActive` / `engineSceneSetActive` store globals (`G_ACTIVE_APP`, `G_ACTIVE_SCENE`) and nearly every other call (`engineGameObject*`, `engineFrame*`, `enginePhysics*`, input) acts on the active app/scene without taking a handle. The API example in `README.md` predates this and is out of date — trust `engine.h`.
- Components are value types across the boundary: `engineGameObjectGet*Component` returns a copy and changes only take effect after `engineGameObjectUpdate*Component`. Internally that is an EnTT `replace`, and `Scene` relies on `entt::observer`s on those updates to rebuild/sync Bullet bodies.
- **Derived data never lives in authored (public) components**: it goes into engine-internal components that the scene computes and that are never saved (world matrix, skin pose, animation controller, children list, nav mesh). The transform component is only the authored local TRS, relative to the parent space (the parent's world matrix, times the joint matrix when the game object has a joint attachment; the world when it has neither). The world matrix is `world_transform_internal_component_t` (`impl/world_transform.h`, GL-free and unit tested), added and removed with the transform component; the game reads it with `engineGameObjectGetWorldTransform`, valid after the last scene update. To write a world matrix back (editor gizmo, physics), convert it with `local_transform_from_world` against `Scene::get_parent_space_matrix`.
- Hierarchy: the parent component is the only thing to set. A game object's children are derived from the parent components of the others (`children_internal_component_t`, kept by `Scene`'s observers, in the order they were parented, no size limit) and are queried with `engineGameObjectGetChildrenCount` / `engineGameObjectGetChild`; any hierarchy change invalidates the indices, so copy the children before destroying or reparenting them (`project_c::utils::get_children`). Destroying a game object (`engineGameObjectDestroy`, also when its `IScript` is destroyed) destroys its children with it; remove a child's parent component first to keep it. Organizing the editor's scene hierarchy view is **not** done with parents: the folder component (`engine_folder_component_t`, a `/` separated path such as `environment/walls`) lists a game object that has no parent in a folder, and has no other effect.
- Adding a component type means touching: the C struct in `include/components/`, the Add/Get/Update/Remove/Has functions in `engine.h` + `engine.cpp`, any default-initialisation in `impl/components_utils/components_initializers`, the consuming system in `scene.cpp`, and (optionally) the properties panel in `application_editor.cpp`.
- `Application` owns the window/GL context, resource atlases (textures, geometries, skins, animation sets, prefabs, shaders — `named_atlas.h`, addressed by handle or name; names must be unique and non-empty, so creation fails otherwise; every asset is **reference counted** (`add_object` gives one reference, `acquire` / `release`, the last release destroys it) and a **handle is slot + generation**, so a handle to a released asset never finds anything again, not even an asset created later in its slot (lookups return `nullptr` / `ENGINE_INVALID_OBJECT_HANDLE`; the renderer skips and logs such draws). Components store handles **without** holding references (they are values copied across the C API): whoever loads an asset holds it, and the names are the asset IDs scene files will use: glTF meshes, embedded images and skins are `<model file>#<name>` (`#mesh_<i>` etc. when unnamed, see `impl/asset_id.h`), e.g. `Rogue.glb#Cylinder.008`, `Rogue.glb#rogue_texture`; an image in its own file is named by its path relative to `assets/models`, so models referencing it share one texture), the `UiManager` and the `Renderer`. `ApplicationEditor` derives from it and is instantiated instead when `enable_editor` is set; it hooks the `on_*` virtuals to add the ImGui dockspace (the scene is rendered into a texture at the size of its scene panel and shown there, see `get_scene_viewport`), editor camera, gizmos, entity picking, undo (`editor_commands`) and the Play/pause + game/editor view state that `engineEditorIsPlaying` / `engineEditorIsGameView` report.
- `Scene` owns the EnTT registry and a `PhysicsSystem` (`impl/physics_system.h`, reached with `Scene::physics()`): the ECS side of physics (body types, creating bodies from their components, syncing them to transforms, forces, writing dynamic bodies back, character moves, queries) around a `PhysicsWorld`, the Bullet side. Keep physics code there, not in `Scene`. `Scene::update` runs animation controllers → physics (sync bodies to the transforms, step, write dynamic bodies back) → world transforms (`update_world_transforms`: TRS, joint attachments, parent→child; writes only the internal component, so no observers fire) → skins, then gathers a `SceneRenderData` and submits it. It never calls the graphics API. **Physics always sees this frame's state, also during the scripts' update** (like Unity: eager bodies, lazy transform sync): a body is created as soon as its collider / rigid body / character controller is added and again when one changes, at the world matrix computed from the current transforms (`compute_world_matrix`, not the world transform component, which is from the last update); moved transforms are synced to the bodies before the physics step and before every physics query (ray cast, character move) when a transform, parent or joint attachment changed (`PhysicsSystem::sync_bodies_to_transforms`). Bodies of game objects with a parent or joint attachment follow it, the others move when their transform changes. Collider sizes are in their game object's space: the shape is scaled by the world scale, inherited from the parents (a hitbox under a character scaled 0.35 is authored in the character's units). **Body types are explicit** (`engine_rigid_body_type_t`, like Bevy/Jolt/Godot): dynamic (moved by the physics, needs mass), kinematic (moved by its transform; Bullet gives it a velocity, so it pushes dynamic bodies) or static (level geometry). A collider without a rigid body is static, or kinematic when it has a parent or joint attachment (hitboxes); an explicit type wins (e.g. static walls parented to a room). The engine never infers a type from movement: a static collider moved by its transform is teleported, and logged once outside the editor. Kinematic bodies pair with dynamic and kinematic ones but not with statics, so a hitbox detects a character (whose capsule is kinematic); static colliders never detect each other; bodies moved by hand go through `PhysicsWorld::set_world_transform`, which also updates their broadphase bounds so ray casts see them immediately (Bullet steps at a fixed 1/60 s, so a frame can have no substep).
- Rendering is a render graph; **read `src/engine/impl/render/README.md` before changing anything under `render/`**. It covers the pass list, how to write a pass, and the `RenderFeature` extension point (post-process and overlay stages). `render_graph.h/.cpp` must stay free of GL so it remains unit-testable.
- Animation: `Skin` + `AnimationController` wrap ozz. A `Skin` is a shared, immutable **asset** in the skins atlas (skeleton + binding to the mesh; the model's prefab creates one per model, not per instance). Each instance's pose (`SkinPose`) lives in an internal component (`skin_pose_internal_component_t`) on the game object with the skin component, created in the rest pose when that component gets its skin; the animation controller on the same game object writes it. Skinned meshes and joint attachments reference that **game object** (`.skin` is an `engine_game_object_t`), not the asset, because the asset alone can't say whose pose to read. A model's clips compiled for its skin are an **animation set** asset (`AnimationLibrary`, atlas name `<model file>#animations`, one per model, created by the prefab). **Controllers are owned by the engine**: the animation controller component holds the animation set handle and the **layer setup as data** (per layer: an optional descriptive name, mode, starting weight, starting looping, joint weights as a mask; layer id = index, scripts address layers by id; a new component has one override layer). When it gets a set (and the game object has a skin), `Scene` creates the controller in an internal component (`animation_controller_internal_component_t`) and it is destroyed with the component, the skin component or the game object; an update with the same set and skin only reconfigures the layers (the controller and its animation events stay). No controller pointer leaves the engine: the `engineAnimationController*` functions take the **game object** and act on its controller. They are runtime commands and queries only (play, cross-fade, is playing, events, and changing a layer's weight / looping / playback rate while playing); the layer setup is never done through calls (like `enginePhysicsAddForce(go, …)` on its body), returning false / an error code when it has none. The editor's stats show the number of live controllers (`AnimationController::get_live_count`).
- **Characters are moved by the engine's kinematic character controller** (`engine_character_controller_component_t`, like Unity's `CharacterController` / Godot's `move_and_slide`, not by physics forces): a capsule standing on the game object's origin (sizes in its scaled space, like colliders). Scripts call `engineCharacterControllerMove(go, velocity, dt, &result)` once per frame with the horizontal velocity they want; the engine adds gravity (keeping the fall speed between moves, in `character_controller_internal_component_t`) and sweeps the capsule (`PhysicsWorld::move_character`): step up, collide and slide horizontally (everything is slid along, never climbed), step down and snap to walkable ground (ledge detection: the edge of walkable ground counts; a step is only taken when it ends on walkable ground). Static and kinematic bodies block it (including other characters), triggers and dynamic bodies don't (its kinematic capsule pushes those). The transform is written right away; while a script doesn't call it (the player's scripted traversal), setting the transform moves the character. Don't combine it with a collider or rigid body; the game object must have no parent.
- **Navigation is engine-owned** (Recast/Detour, `impl/nav_mesh.h`). Authored: one **nav surface** component per scene (agent radius/height/max slope/max climb, cell size/height) and optional **nav modifier** components (like Unity's `NavMeshModifier`: walkable = included by the normal rules, the default; not walkable = obstacle; ignore = left out; children inherit their closest ancestor's). `engineNavMeshBuild()` rasterizes the scene's **static colliders** at their world transforms (colliders of kinematic rigid bodies, dynamic ones with mass and triggers are skipped; without a modifier the slope decides what is walkable) into one single-tile nav mesh, logs its triangle count and build time, and keeps it in an internal component on the nav surface's game object (`nav_mesh_internal_component_t`: derived data, never saved, destroyed with the surface). Nothing rebuilds it automatically: build it after placing or loading the level and again after static colliders changed. Floors made of many tiles need no merging, Recast voxelizes all input into one heightfield. Queries take the caller's search extents for snapping points onto the nav mesh: `engineNavFindPath` (string-pulled corners, start first, with a complete/partial status; partial when the end is unreachable, e.g. on a disconnected island, then it ends at the closest reachable point) and `engineNavFindNearestPoint`. The editor has a nav mesh debug-draw toggle (scene options) and a "Build nav mesh" button under the Nav Surface component (the bake: after editing the surface, modifiers or static colliders).
- **Prefabs are engine assets** (`impl/prefab.h`, `prefabs` atlas, named by the model file, e.g. `Rogue.glb`): `enginePrefabLoad` parses a glTF file and creates its geometries, textures, skin and animation set as assets (the `<model file>#<name>` IDs above) which live as long as the prefab; loading a file which is loaded already returns the same prefab with one more reference. An image in its own file is a dependency, not a sub-asset: each prefab using it (and the game, if it created it with `engineTexture2DCreateFromFile`) holds a reference, so it lives as long as the last of them. `enginePrefabRelease` drops the caller's reference; every instance holds one too, so a prefab is destroyed (with its assets) when the game has released it and its last instance is destroyed, at the latest with its scene. Release prefabs before their application is destroyed, and keep a prefab loaded while game objects which aren't its instances use its assets (e.g. the player's weapon uses `Rogue.glb#Cylinder.008`; the game holds its prefabs for its whole run). `enginePrefabInstantiate` stamps the model's node hierarchy into the active scene (joints of the skin become no game objects, the root parents everything) and marks the root with an internal `prefab_instance_internal_component_t` (`enginePrefabInstanceGetPrefab`; it holds the instance's reference to the prefab), the link a scene file will save. The glTF parser's model description (`ModelDesc`) is internal: the C API has no model/mesh/skin desc types.
- `impl/imgui` and `impl/imguizmo` are vendored copies compiled into the engine, not the submodules of the same name.
- Shaders live in `assets/shaders`; the `#version` line is added implicitly by the engine, so shader files must not declare it. `*.h` files there are shared GLSL includes.

### Toolkit (`src/engine_app_toolkit`)

Thin C++ wrappers over the C API that define the game-side object model:

- `IApplication` creates the engine application and owns a `SceneManager` (scenes are registered by type and looked up by their static `get_name()`).
- `IScene` owns one engine scene and a map of `engine_game_object_t → IScript`. One script owns one game object.
- `IScene::update` defines the frame order: flush newly registered scripts → (if playing) `update_hook_begin`, dispatch physics collisions to `on_collision`, `update`, `late_update` → `engineFrameSceneUpdate` → drop scripts whose game object was destroyed → `update_hook_end` → flush unregistrations. Script registration and unregistration are **deferred through queues**, so a script registered this frame is not in the map until the next `update`.
- `utils.h` has the `set_c_array` / `to_array` helpers for the C-array fields in component structs, and `log()`.

### Project C (`src/games/project_c`)

- `default_prefabs_data()` (`app.cpp`) maps `PrefabType` → glTF file; `AppProjectC` loads each as an engine prefab once at startup (and releases them in its destructor); `instantiate_prefab()` instantiates one into the active scene and returns its root as a `PrefabResult`.
- `main.cpp` registers the level scene and owns the main loop, which holds only platform concerns: `engineFrameBegin` → read the devices into `PlayerInput` → quit (window closed or the `quit` action) → `AppProjectC::update(dt)` → `engineFrameEnd`. `AppProjectC::update` is one game frame: update the scenes, then apply scene changes they requested (`request_scene_reload<T>()`, deferred because a scene can't replace itself mid-update). Scenario tests call the same function. **Level rules live in the scene** (`TestScene::update` override: gameplay UI visibility, restart once the encounter is over), never in the loop and not in `AppProjectC`, which stays level-agnostic. There is a single level, `scenes/scene_test.cpp`: it builds the ASCII map with `LevelBuilder`, builds the nav mesh (`engineNavMeshBuild`) once the map is placed, and adds the camera, light, `Encounter` and `GameplayHud` scripts.
- **Gameplay scripts never depend on the scene class.** Win/lose rules are the `Encounter` script (`scripts/encounter_script.h`: cleared when every enemy is dead, defeated when the player is), and the HUD is the `GameplayHud` script (owns the RmlUi document `assets/ui_docs/project_c_gameplay_ui.rml` and its data bindings). Both *read* the Player/Enemy/Weapon scripts every frame; nothing reports to them. Scripts that need them use `my_scene_->find_script<Encounter>()` and must handle `nullptr`: a scene without an encounter or HUD (e.g. a scenario test scene) still plays.
- `scenes/level_builder.h` places the nav surface, floor tiles (`floor_not_walkable` adds a not-walkable nav modifier), walls, static obstacles, the player (with its weapon), enemies, chests and weapons. The level and the scenario tests both build with it.
- Gameplay objects are scripts deriving from `BaseNode` (`scripts/base_script.h`), which is `IScript` plus a name component and prefab-aware constructors. Player and enemy logic are hand-written state machines driving animation-controller layers and animation events; scripts find each other through `my_scene_->get_script<T>(go)` (returns `nullptr` when the game object has no script of that type), or `find_script<T>()` / `get_scripts<T>()` for scripts that aren't tied to a known game object.
- `CameraScript` follows the player with a spring and shifts toward the mouse cursor (look-ahead). Occlusion is handled only by the house itself: while the player is inside, `House` hides the roof (and the props on it) and the camera facing wall.
- Player traversal and camera occlusion are documented in `src/games/project_c/CLIMBING_AND_OCCLUSION.md`. Player traversal (climb a wall, vault through a window, climb down a roof edge, mantle onto the roof at the top of a climb) starts automatically when the player walks into the obstacle; a pulsing marker shows the nearest available action whenever the player is close to a wall, window or roof edge. On the wall, WASD keeps its ground meaning: toward the wall climbs up, away climbs down. It is raycast-driven and only reacts to colliders owned by `BuildingPart` scripts (`scripts/building_script.h`). While traversing, the traversal code sets the player's transform and its character controller isn't moved; walking (and falling) resumes when traversal ends. The `House` is built over the `h` cells of the ASCII map in `scene_test.cpp`; those cells get floor tiles with a not-walkable nav modifier, so enemies don't path into the house. Enemies query paths with `engineNavFindPath`; the scenario `SandboxScene` builds its nav mesh before its first step.
